# Marao Home Assistant integration

Use the repository contract and selected OpenSpec requirements as the acceptance
criteria. This skill adds Python and Home Assistant implementation guidance;
[project context](../../../openspec/project-context.md) maps the existing modules.

## Find the affected boundary

- Lifecycle or administrative API: trace setup/unload, registration, authorization,
  validation, and the editor caller in both directions. Preserve existing command
  shapes and separate retryable setup failures from invalid input or authentication.
- Configuration or generation: trace editor validation through the canonical model,
  conversion, generator, protected output, and history. Consult the
  [integration lifecycle spec](../../../openspec/specs/integration-lifecycle/spec.md)
  for preservation and recovery before changing saved formats or defaults.
- HA API changes: inspect the installed dependency and supported release first.
  Use the official sources below to verify the specific API; current upstream
  examples do not establish support in Marao's installed version.

## Python and async decisions

- Use the repository's Python 3.14 environment and pinned dependencies. Keep pure
  model/generation helpers independent of HA lifecycle code where already separated.
- Keep blocking filesystem and generation work out of the event loop. Follow the
  existing `hass.async_add_executor_job` boundary; move the complete blocking
  operation together, including reads/writes after opening a file. Do not call
  `asyncio.run()` inside HA or introduce a second event loop.
- Give tasks and subscriptions a lifecycle owner. Match the surrounding HA task
  helpers, release resources on unload, and preserve cancellation through cleanup.
  Avoid adding a coordinator or another abstraction for work the existing owner handles.
- Keep validation and authorization at the real write boundary. Preserve read-only
  preview paths, operation errors, and recovery information rather than converting
  failures into defaults or apparent success.
- Keep config-entry version, persisted dashboard format, and package version
  separate. Reuse the ordered conversion/validation path across all affected callers;
  independently specified historical expectations must not be generated by that path.

## Verify the changed behavior

Use [focused testing](../../../docs/docs/development/focused-testing.md) to select
coverage. Reuse the existing HA fixtures in
[backend tests](../../../tests/components/marao_dashboard/); for new nontrivial
logic, assert the observable outcome and relevant failure or preservation case.
Use the existing Node tests when a change crosses the editor model boundary.
A quality-scale audit, broad dependency upgrade, or new test framework is not part
of an ordinary backend change. Live checks use the
[local development workflow](../../../docs/docs/development/local-development.md).

Before reporting a software task done, install all applicable final changes on
disposable HA `192.168.10.229`, even when the user handles visual testing. Batch
backend/fixture changes into one `npm run ha:sync` and one necessary restart near
handoff; use lightweight frontend sync for compatible frontend-only changes.
Leave successful assets installed. The installation's current-asset/readiness
checks suffice; do not add a test campaign. If blocked, report not installed /
not ready for test. Instructions/docs with no runtime effect need no deployment.
