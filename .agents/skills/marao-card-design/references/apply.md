# Scope and safe promotion

Inspect the final diff against proposal.json baseline. Record requested card, behavior owner, direct consumers, owned popup/generated roles, intended differences and invariants. The ownership map is a starting point, not automatic proof of impact. Cross-check tests/verification-map.js and actual call sites. Generated native wrappers delegate; distinct custom element names do not imply distinct owners.

Example: target-number styling may affect Climate + its details, Number and Wallbox. Ask: “Apply to all these consumers, only Climate and its details, or a specified subset?” Record the explicit choice with proposal revision and affected consumers. Main-only vs popup-only requires a correspondingly scoped variant. Do not ask again for an unchanged explicit choice.

Before writing main: obtain apply authorization, recompute consumers from the final patch, compare every destination against proposal.hashes and inspect concurrent edits. Safely rebase in the proposal workspace if needed; never overwrite drift. Renew scope approval when intended behavior or affected consumers expand. A nonconflicting rebase can retain approval only when approved hunks and semantic scope are unchanged.

Use `npm run card:apply -- --task <id>` for every approved preview application. Do not substitute manual patch/copy/deploy steps. The task must belong to this source checkout. Preserve unrelated work and existing staging.

1. Finish related editor, configuration, translation and documentation wiring in the preview. Inspect `git diff` against `proposal.baseline`, the independent preview baseline, and recompute affected consumers. Older previews default to their current HEAD, checked against recorded file hashes; reconcile an older task's baseline if those hashes disagree. Reconcile source drift before proceeding; keep approval when reviewed hunks and semantic scope remain unchanged.
2. Set `proposal.review` initially to `{ "files": ["<editable source path>", "<related documentation/test path>"], "tests": ["tests/frontend/<relevant>.test.js"] }`. Select only the reviewed source changes; omit generated bundles, copied baselines, caches, fixtures/private data and unrelated work. The command supports frontend source/runtime, documentation, tests and OpenSpec files. Backend, fixture or dependency changes need their existing dedicated workflow. Use a minimal existing Node unit test for nontrivial logic; visual-only changes may use `tests: []`. No full/integration/browser suite is implied.
3. Run `npm run card:apply -- --task <id> --plan`. Review its file list, excluded changes and conflicts. The plan performs no source writes or HA calls. Record the returned `review` object verbatim in `proposal.json` once it matches the authorized patch. Keep `designApproved` and `applyAuthorized` true only with the user's authorization; record `scopeDecision.behavior`, `consumers`, `proposalRevision` and `authorization`. Reuse an unchanged explicit choice without another approval question. The review digest binds the patch, revision, tests and consumer scope; further edits require a refreshed review.
4. Run `npm run card:apply -- --task <id>`. It checks baseline hashes, refuses destination drift, preflights the exact patch, saves private before-file backups, applies without staging, rebuilds and runs the selected checks serially, then calls the existing `prepareFrontend()` installer. Already-applied files are recognized, so a failed check/install can be fixed and retried. Runtime installation is restricted to disposable `192.168.0.28`; no dashboard/helper reset or automatic full preparation occurs. Documentation/test-only patches need no installation.
5. Read the result. The task workspace's `.application/<run>/receipt.json` records checks and verified installation identity without credentials. Failures retain backups and never count as ready for test. Resolve the reported issue and rerun the command; do not silently bypass it. If a terminated process left `.card-design/apply.lock`, verify that no apply is running and reconcile retained source/recovery state before removing that stale lock.

The script cannot infer whether a design is complete or which consumers the user approved; the agent retains that review responsibility. Report the test URL and a short manual watch list after successful installation. No publishing is implicit.
